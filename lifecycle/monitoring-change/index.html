    Lifecycle chapter 8

    Monitoring and Change

    Monitoring explains what current evidence means; change control decides what authorized direction should change.

    Monitoring turns observations into decisions

    Monitoring is not the same as collecting status data. Work performance data are raw observations such as dates, costs, defects, completed items, and test results. Analysis gives those observations context and produces work performance information. Selected information is then organized into work performance reports for stakeholders who need to understand status, forecasts, risks, or decisions.

    For example, “migration test 17 failed” is data. Comparing failures across test cycles and identifying a rising error rate produces information. A report that explains the trend, its forecast effect, and the decision required gives governance a usable view.

    Issues, impediments, and risks

    A risk is uncertain. An Issue Log records a condition that already exists, who owns the response, when action is due, and when escalation is required. An impediment is something blocking or slowing work. A team may remove a small impediment immediately; a material or persistent impediment may become a project issue and require escalation.

    The label matters because the response changes. Risks are analyzed before they occur. Issues need current action. Impediments need flow restored. The records may link to one another, but they should not hide the current state of the problem.

    A change moves through distinct states

    A Change Request is a proposal. It explains what should change, why, and what approved commitments may be affected. Impact analysis examines scope, schedule, cost, quality, resources, risk, contracts, compliance, benefits, and stakeholder effects.

    The authorized change role then approves, rejects, defers, or requests more information. Approval changes the decision state; it does not implement the work. The approved change is communicated and assigned, the team implements it, affected plans and baselines are updated under control, and the result is verified. The Change Log preserves that trace.

    This sequence prevents four different things from being collapsed into one word:

    1. requested change;
    2. approved change;
    3. implemented change;
    4. verified change.

    For ServiceBridge, a request to strengthen encryption is analyzed for design, cost, schedule, seller, and compliance effects. The change authority approves it. The delivery team implements it. Security testing verifies the result. Only then can the log show both the decision and its completed implementation evidence.

    Adaptive teams may reprioritize uncommitted backlog detail without a formal baseline change. A change to a controlled release, contract, compliance obligation, funding limit, or other approved commitment still follows the relevant authority route. Hybrid projects must make that boundary explicit.

    For the exam, assess first, follow the approved change process, update affected records after the decision, and verify the implemented result. Urgency does not give the project manager unlimited authority.

    Local sequence

    1. Capture work performance data from execution and relevant external conditions.
    2. Analyze domain results into Work Performance Information.
    3. Integrate status, variance, trends, forecasts, risks, issues, and dependencies through Monitor and Control Project Work.
    4. Communicate decision-ready Work Performance Reports.
    5. Resolve issues within delegated authority or escalate through the named governance route.
    6. Document proposed changes as Change Requests, analyze impacts, and obtain an authorized disposition.
    7. Implement approved changes, update controlled records, and verify the resulting work.

    Handoffs and return loops

    What enters

    Actual results, forecasts, defects, risks, issues, stakeholder feedback, agreement performance, and current plans.

    What this work accomplishes

    Creates integrated understanding and authorized responses while preserving configuration and decision history.

    What moves next

    Actions return to execution; approved changes update affected owners; rejected requests leave baselines unchanged; verified results proceed to acceptance.

    Control is continuous. A defect can return to correction and reinspection. A variance can prompt analysis, corrective action, or change. A new issue can reveal a risk response failure. Stakeholder feedback can require engagement adjustment without necessarily changing scope. Every return path needs an owner and an authority boundary.

    Issues, impediments, and configuration

    An issue is a current condition requiring action; a risk is uncertain. An impediment blocks or slows progress and may be an issue, organizational constraint, dependency, or policy concern. The lifecycle guide makes these relationships explicit, but dedicated issue-log and impediment destinations remain deferred because current repository sources do not yet support responsible standalone pages.

    Version and configuration controls preserve which approved artifact state applies. A changed working document, an approved change, and an updated baseline are different events.

    Approach treatment and exam distinctions

    Predictive control often compares performance with broader baselines. Adaptive control uses frequent review of outcomes, flow, quality, and feedback within governance guardrails. Hybrid control must integrate both evidence types without forcing one cadence to masquerade as the other.

    Data, information, and reports are not interchangeable. Corrective action is not automatic baseline change. Only the authorized role or body may approve a controlled change. Approved change implementation must be verified.
